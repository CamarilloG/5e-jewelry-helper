# 1.0.2 迭代文档

> 2026-11-08 · 草案 · 基于 1.0.1（main `866d76e`）· 证据见[验证记录](验证记录.md)“搜索关键词语义实测”

## 1. 背景

- **默认方案太慢**：1.0.1 每个候选账号都要读一次完整库存。全局限速每分钟 30 次，每个候选至少约 2 秒；默认方案的四把刀一行就有几百个候选，要十几到几十分钟。
- **关键词缺陷**：实测发现平台搜索不是“名称包含”匹配。1.0.1 词典里的「格洛克」「加利尔」在真实平台搜不到结果；内置方案含格洛克这一行，会被误判为空结果。
- **缓存没用上**：本地已经缓存了账号库存和快照，但筛选时不用。只改价格、租期这类小条件，也要从头重扫。
- **收藏卡片利用率低**：收藏监测每行只有一张缩略图，大量空白。

## 2. 范围

### A. 搜索与筛选（必须）

| 编号 | 内容 | 验收 |
|---|---|---|
| A1 | **关键词全部实测**：每个子类的搜索关键词必须在真实平台验证过，且只命中该子类（“精确”）或至少覆盖该子类（“宽”）。已验证：蝴蝶刀、M9刺刀、锯齿爪刀、格洛克18型、M4A1、AK-47、USP、SG553、SSG08、加利尔AR、CZ75、R8、裹手、手套。其余约 45 个子类用一轮只读请求（约 45 次）补测 | 词典每个关键词带“已验证日期”和“精确/宽”标记；单元测试校验无空格、无未验证项 |
| A2 | **搜索为 0 的保护**：未验证或可疑的关键词返回 0 时，不判定该行为空，改为由库存确认把关；只有已验证关键词返回 0 才提前结束 | 回归：关键词返回 0 但库存里有该饰品的账号仍被找到 |
| A3 | **搜索结果直接判定**：平台搜索按完整库存匹配（已实测）。只选了类别、没选皮肤，且关键词精确的行，搜索命中即判定满足，不读库存；整个方案都是这类行时，全程不读库存 | 默认方案在真实平台的请求数 ≤ 各行搜索页数之和 + 最终结果数；回归用例统计库存接口调用为 0 |
| A4 | **大类展开**：「任意手套」=「手套」∪「裹手」，「任意刀」= 各刀型关键词并集，其他大类同理；大类行也参与缩小候选 | 默认方案不再出现“浏览全部账号”提示 |
| A5 | **仍需读库存的行**：同一行同时有类别和皮肤（同一件约束）、关键词只是“宽”（如「刺刀」会带出 M9 刺刀）。按现有逻辑逐个确认，并沿用“剩余页数多于候选时不再翻页”的规则 | 现有同件约束用例全部保留通过 |
| A6 | **结果先出、状态后补**：交集一确定就列出账号，标“状态确认中”，后台逐个确认租赁状态后更新 | 界面在状态确认完成前已显示结果 |
| A7 | **搜索结果短时缓存**：同一关键词 + 租期 + 仅可用券，5 分钟内复用分页结果 | 5 分钟内重复筛选不再发送搜索请求 |
| A8 | **虚拟平台按真实规则匹配**：离线虚拟平台的搜索改为实测规则（带空格搜不到；未登记的前缀搜不到），避免离线测试再次掩盖关键词问题 | 用旧关键词「格洛克」的离线用例结果为 0 |

### B. 本地缓存优先（必须）

| 编号 | 内容 | 验收 |
|---|---|---|
| B1 | **上次结果**：每次筛选完成后，按条件保存结果（账号、命中件数、命中饰品、完成时间），重启后保留。同条件再次筛选时立即显示，注明“上次结果 · N 分钟前 · 正在刷新”；刷新完成后整体替换，不再符合的账号此时才移除 | 同条件第二次筛选在发出任何请求前就显示结果 |
| B2 | **本地预算**：对任意条件，先用本地已缓存完整库存的账号在本机算一遍并立即显示，注明“来自本地缓存的 N 个账号”；平台结果陆续补进来 | 断网时仍能看到本地预算结果，并提示结果不完整 |
| B3 | **小条件变化**：饰品条件不变，只改价格、仅可用券、租期时，按下表处理 | 见下表 |
| B4 | **缓存每个账号满足了哪几行**：把“该账号满足了哪几行条件”和完整库存一起缓存，价格、租期变化时只在本地重新组合 | 改价格不触发库存请求 |
| B5 | **库存缓存默认有效期**：从“本次运行”改为 6 小时；已手动改过该设置的用户保持原值 | 新装默认 6 小时；从 1.0.1 升级、设置为其他值的保持不变 |

B3 规则：

| 改了什么 | 处理 |
|---|---|
| 收紧（价格上限调低、下限调高、勾选仅可用券） | 上次结果的子集即为准确结果，立即显示，**不重新搜索**，只补确认租赁状态 |
| 放宽（价格上限调高、去掉仅可用券） | 先显示本地子集，再搜索补入被价格挡掉的账号 |
| 换租期 | 账号快照含六种租期价格，饰品判定与租期无关；先用本地已知账号算出结果，再按新租期搜索补全，库存已缓存的账号不再读取 |
| 改了饰品条件 | 走 B2 本地预算，再完整筛选 |

**状态规则（B 全部适用）**：缓存中的租赁状态只作参考，卡片标“状态待确认”，不把旧状态显示为“可租”。一键出码仍以平台实时预检为准。

### C. 收藏监测卡片（应当）

| 编号 | 内容 | 验收 |
|---|---|---|
| C1 | **卡片内 3×3 饰品宫格**：仍是一行一个收藏，用 9 格宫格代替现在的单张缩略图，每格是缩略图，悬停显示名称、磨损与估价 | 1200×760 与 1440×900 下卡片无大片留白、不溢出 |
| C2 | **挑选顺序**：先取刀、手套、主战武器（步枪 + 狙击步枪）各自估价最高的 2 件，按估价排列；不足 9 格时，从其余饰品中按估价从高到低补满；不足 9 件则留空格 | 单元测试：各类不足 2 件、总数不足 9 件、同价排序稳定 |
| C3 | **数据来源**：优先用该账号的完整库存缓存；没有时用搜索展示位（最多 5 件），并在后台以最低优先级补读一次完整库存，读完更新卡片。宫格结果随收藏摘要保存，重启后直接显示 | 新收藏先显示展示位，库存读完后变成完整宫格；补读计入限速 |

## 3. 不在本次范围

精细筛选（图案、磨损、StatTrak、贴纸）、续租、Windows 10 矩阵、对外发布。

## 4. 已确认与待确认

已确认（2026-11-08）：
- A–C 三部分都做；B3 小条件变化先走本地缓存，再继续筛选。
- 收藏卡片采用卡片内 3×3 宫格；刀、手套、主战各取估价前两件，剩余格子按估价补满。
- 搜索结果缓存 5 分钟。

待确认：
1. **主战武器的范围**：本文暂按“步枪 + 狙击步枪”（AK-47、M4A1、M4A4、AWP 等），手枪、冲锋枪不算。
2. **补测请求**：A1 需要约 45 次只读搜索请求，开工时执行。

## 5. 验证计划

- **离线**：类型检查、静态检查、全部单元测试；新增用例覆盖 A2、A3、A4、A7、A8、B1–B5。
- **真实平台（只读）**：A1 补测关键词；用内置方案实际筛选一次，记录请求数与耗时，对照 1.0.1。
- **界面**：离线预览中验收“上次结果”提示、本地预算、状态待确认标注，以及收藏卡片的 3×3 宫格。
- **交付**：更新接口规范、状态机与产品文档；打 1.0.2 安装包，补版本说明与验收记录。
