## 4. 收藏写回：通过并恢复

**真实外部写入，结束时恢复原状态。**

按 `favorites/update` 的目标状态执行新增，重复提交相同状态，使用详情确认变化；随后恢复原收藏状态，再读详情确认恢复。各请求均成功，原收藏集合未因验证留下新增项。

重复设状态可被平台接受；本地仍固定使用串行队列、最新 revision 和移除记录，防止用户快速反向操作被迟到响应覆盖。程序保留 `finally` 恢复逻辑和核对断言。

## 5. 支付闭环：通过

**用户明确授权的真实订单，支付由用户本人完成。**

1. 重新读取账号、时长、协议和渠道，核对 2 小时合计 ¥0.20，执行锁号预检。
2. 仅发送一次创建请求：`buyTimeType=1,buyCount=2,payChannel=1,realAmount="20",propId=0`，渠道 ID 来自本次渠道接口。
3. 平台返回支付订单 ID、付款码图片、截止时间及 181 秒初始剩余时间。付款码按平台图片展示，没有二次编码成另一张二维码。
4. 用户扫码后，`get_status` 返回 `payStatus=1,abnormalReason=0`。
5. 只读核对租赁记录：金额 `"0.2"` 元、租期 `"7200"` 秒、订单状态 1。本轮支付订单 ID 与租赁订单号不同；租赁订单号和子订单号相同。

创建请求的金额是**分**，租赁记录和详情金额是**元**。三个订单字段按接口用途隔离，不能靠格式或数值相同推断可互换。验证没有自动付款、没有上号，没有对已支付订单解锁，也没有额外创建未支付测试订单。

取消和超时流程采用公开前端的 `unlock_account` 调用及支付状态分支作为依据；该接口成功只证明释放请求被接受，不能证明租赁订单已经取消。因此规范固定为先核对支付、只发送一次释放、持久化恢复记录、结果不明时阻止重复出码。

通知证据证明原生提交、动作载荷和系统激活链路；没有把 `show` 事件表述为用户已经看到并手点了系统通知按钮。冷启动不依赖 COM 激活，正式路线固定为安装器注册协议，兼容系统抑制通知时只显示应用内状态的规则。[Electron Notification](https://www.electronjs.org/docs/latest/api/notification)、[Microsoft 激活回调](https://learn.microsoft.com/en-us/windows/win32/api/notificationactivationcallback/nf-notificationactivationcallback-inotificationactivationcallback-activate)、[NSIS](https://www.electron.build/nsis.html)

样例默认卸载后发现运行时注册的 URI scheme 和 COM CLSID 残留；本轮核对目标路径后执行清理，被环境执行策略拒绝（`blocked by policy`）。验证程序文件、进程和快捷方式已经移除，两项测试注册保留在本机。正式安装路线因此固定加入归属校验的 NSIS 卸载钩子，覆盖升级保留注册；该规则已进入 M1-05 与 M6-03 验收，不依赖默认卸载器自动处理运行时注册。

固定依赖和安全边界依据本轮实际运行，SQLite 通过适配器隔离，不承诺其上游 API 永不变更。[Electron 安全](https://www.electronjs.org/docs/latest/tutorial/security)、[Node SQLite](https://nodejs.org/api/sqlite.html)、[Biome 配置](https://biomejs.dev/reference/configuration/)

## 8. 验证结论的适用范围

本轮证据已足以固定技术路线、接口适配和开发流程，没有遗留选型分支。正式应用按 [开发任务与验收](开发任务与验收.md) 实现；完整页面、数据库迁移、Windows 10/11 发布矩阵和安全回归属于这些实现任务的完成标准。

复查采用 [验证程序说明](../tools/validation/README.md) 中的离线命令。真实交易脚本不在常规测试命令里，避免测试运行者无意创建订单。公开摘要只保留字段名、状态、数量和文件校验和，不含真实账号、凭证和订单标识。

文档检查已通过：本地链接可达、代码围栏成对、JSON 和 Python 语法正确，文档均为正式基线且不含 JWT 形状文本；付款码、个人订单上下文、依赖和构建目录均命中 Git 忽略规则。
